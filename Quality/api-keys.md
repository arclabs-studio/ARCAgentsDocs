# 🔑 Client Secrets & API Keys

**Where does a key go? The answer depends on whether it's a real secret or a client-public identifier — never on how "hidden" it looks in the binary.**

---

## 🎯 First Principle

**Anything shipped in an app binary is extractable.** `strings`, `class-dump`, a jailbroken device, or a runtime hook (Frida) recovers it. Obfuscation only raises the bar against casual/automated scraping — it is *never* a security control.

So the model is:

- **Real secrets** → never reach the device. Proxy through a backend.
- **Client-public keys** → ship them, but restrict them at the provider so a leaked copy can't be abused.

---

## 🌳 Decision Tree

```
Is the value used for server-to-server calls, signing, or anything
that grants privileged access if leaked?
│
├─ YES → REAL SECRET
│        • Never put it in the app, Info.plist, xcconfig committed to the repo,
│          or an obfuscated blob.
│        • Store in a backend secret manager (Firebase Secret Manager,
│          Cloud Secret Manager, Vault, GitHub Actions secrets for CI).
│        • Expose via an authenticated Cloud Function / API the app calls.
│        • Examples: OpenAI/Grok API keys, Google Places key (server-side),
│          Apple Maps `.p8` private key, any DB / admin credential.
│
└─ NO → CLIENT-PUBLIC KEY (an identifier the SDK needs on-device by design)
         • Inject at build time: xcconfig → Info.plist → read at runtime via
           `ARCStorage.ConfigurationValue.string("KEY_NAME")`.
         • Keep the real values in gitignored `Secrets-*.xcconfig` files;
           commit only `Secrets.xcconfig.example` with placeholders.
         • Restrict the key at the provider (bundle-ID restriction, API
           restrictions, abuse quotas).
         • Examples: Firebase iOS API key (in GoogleService-Info.plist),
           RevenueCat public SDK key (`appl_…`).
         • OPTIONAL defense-in-depth: obfuscate the literal (see below).
           Cosmetic only — do not rely on it.
```

---

## 🛠️ The Pattern (client-public keys)

**1. Declare the build setting** in `Secrets.xcconfig.example` (committed, placeholder) and in `Secrets-Dev.xcconfig` / `Secrets-Pro.xcconfig` (gitignored, real values):

```
RC_API_KEY = appl_realKeyFromDashboard
```

**2. Wire it into `Info.plist`:**

```xml
<key>RC_API_KEY</key>
<string>$(RC_API_KEY)</string>
```

**3. Read it at runtime** via ARCStorage:

```swift
import ARCStorage

let apiKey = ConfigurationValue.string("RC_API_KEY") ?? ""
```

`ConfigurationValue.string` returns `nil` (and logs a warning) when the build
setting is absent — e.g. a contributor without the `Secrets-*.xcconfig` files —
so the app degrades gracefully instead of crashing.

**4. Restrict the key at the provider.** A committed key is in git history
forever; restriction is what makes that acceptable:
- **Google Cloud / Firebase API key**: Console → Credentials → API key →
  *Application restrictions* = iOS bundle IDs; *API restrictions* = only the
  Firebase APIs you use. Pair with **App Check** enforcement on Firestore /
  Functions / Storage.
- **RevenueCat**: nothing to restrict — the public SDK key is meant to ship;
  protection is server-side receipt validation. Never use the *secret* API key
  in the app.

## 🌫️ Optional: Light Obfuscation

For client-public keys you can keep the literal from showing up in a plain
`strings` dump. **This is a speed-bump, not security.**

Generate the blob with the ARCDevTools codegen:

```bash
swift Packages/ARCDevTools/scripts/key-obfuscator.swift "appl_realKey" --name rcAPIKey
```

It prints a declaration to commit in your app (e.g. `Obfuscated.swift`):

```swift
// Generated by ARCDevTools/scripts/key-obfuscator.swift — light obfuscation, not a secret store.
// Reconstruct at runtime: ConfigurationValue.deobfuscated(rcAPIKey)
let rcAPIKey: [UInt8] = [0x2C + 0x35, 0x14 + 0x5C, /* … */]
```

Reconstruct at runtime:

```swift
let apiKey = ConfigurationValue.deobfuscated(rcAPIKey) ?? ""
```

**Do not** obfuscate real secrets — that just hides a fire, it doesn't put it
out. And don't bother obfuscating keys that are already documented as public
(Firebase API key, RevenueCat SDK key) unless a stakeholder specifically asks;
it changes nothing about the actual threat model.

---

## ✅ Checklist (per app)

- [ ] No real secret appears in source, `Info.plist`, a committed xcconfig, or an obfuscated blob.
- [ ] Real secrets live in a backend secret manager and are reached via an authenticated proxy.
- [ ] Client-public keys flow xcconfig → `Info.plist` → `ConfigurationValue.string(_:)`.
- [ ] `Secrets.xcconfig.example` committed with placeholders; `Secrets-*.xcconfig` gitignored.
- [ ] Firebase / GCP API keys are restricted (bundle ID + API list); App Check enforced.
- [ ] `GoogleService-Info.plist` being committed is documented as intentional (it is not a secret once the key is restricted) — do **not** rewrite git history over it.
- [ ] CI secrets are in the CI provider's secret store, never in the repo.
